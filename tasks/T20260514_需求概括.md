# Just_codding — AI自动化代码开发Agent 需求概括文档

## 一、项目一句话定义

一个基于Web UI的Python AI代码开发助手。编排DeepSeek API，模拟多名开发角色（需求分析师、开发者、审查者、调试侦探）协同完成**增量开发（DEV）**和**BUG修复（DEBUG）**两个标准工作流。人只需在需求澄清和最终验收两个环节介入，中间全自动运行。

---

## 二、用户使用流程

### 2.1 开发新功能（DEV工作流）

```
用户打开浏览器 → 工作台首页

1. 点击 [我要开发]，在输入框描述需求：
   "给审批模块加一个批量通过功能，支持多选一键审批"

2. Agent 进入澄清对话，追问5个关键问题：
   - 最终交付物是什么？一个接口还是一个页面？
   - 涉及哪些现有模块？给一下文件路径。
   - 核心业务逻辑是怎样的？正常流程描述一下。
   - 有没有特殊约束？比如性能要求、兼容性。
   - 验收标准是什么？怎么算"做完了"？

3. 用户逐一回答 → Agent判断信息够了 → 自动放行，产出澄清文档

4. 进度面板全程自动运行：

   状态: 🟢 需求分析中 — 自动运行
   状态: 🟢 开发规划中(Plan) — 自动，分析方案
   状态: 🟢 开发中(Build) — 自动，写代码
   状态: 🟢 审查中 — 自动，查逻辑+规范
   状态: 🟢 修复中 — 自动，修审查问题
   状态: 🟡 等待你验收 — 请本地编译验证新功能

5. 用户在本地编译运行，亲手验证：
   - 新功能流程走通？没有崩溃？ → 点 [通过]
   - 有问题 → 点 [不通过]，Agent回到修复循环再跑一轮

6. 总结面板弹出："开发完成 ✅ | 费用3.2元 | 3文件修改 | 审查2轮通过"

7. 用户自己执行 git commit，流程结束
```

### 2.2 修复BUG（DEBUG工作流）

```
1. 点击 [我要修BUG]，输入：
   "审批流并发操作时会重复审批"

2. Agent 进入澄清对话，追问BUG细节：
   - 复现步骤是什么？操作1→2→3之后出现什么？
   - 期望行为是什么？
   - 有相关日志或截图吗？贴过来。
   - 最近改过相关代码吗？什么时候？

3. 用户回答 → 信息够了自动放行，产出澄清文档

4. 自动诊断：

   状态: 🟢 诊断分析中 — 分析根因...
   ↓
   [条件分支：论据够不够定位根因？]
   ├─ 够了 → 直接进入修复
   └─ 不够 → Agent自动加日志打点代码
             状态: 🔴 等待你 — 请复现BUG后粘贴新日志过来
             用户复现BUG，贴新日志 → 回到诊断，已有充足论据

5. 自动修复+审查：

   状态: 🟢 修复中 — 自动
   状态: 🟢 审查中(第1轮) — 查逻辑
   状态: 🟢 审查中(第2轮) — 查规范
   状态: 🟡 等待你验收 — 按BUG步骤复现2-3次，确认修好了

6. 用户验收 → [通过]/[不通过]

7. 总结面板 + 手动 git commit
```

### 2.3 人必须参与的节点（共4个）

| # | 环节 | 工作流 | 人做什么 | 耗时 | 能不能省 |
|---|---|---|---|---|---|
| 1 | 澄清对话 | DEV + DEBUG | 描述需求/BUG，回答追问 | 5-10分钟 | ❌ 必须，不知道要什么谁也干不了 |
| 2 | 日志复现 | DEBUG | 复现BUG，粘贴新日志 | 3-5分钟 | ❌ 必须，agent没法替你点你的App |
| 3 | 人工验收 | DEV + DEBUG | 编译跑起来，亲手验证功能 | 5分钟 | ❌ 必须，agent能编译但不能替你看界面 |
| 4 | 代码提交 | DEV + DEBUG | git commit | 10秒 | ❌ 必须，安全红线，防止自动提交错误代码 |

### 3.2 核心设计思想：角色上下文隔离

**问题**：普通Agent把全部上下文塞给一个模型，模型"什么都看见"，容易思维惯性、审查不客观。

**方案**：模拟真实开发团队。每个角色是**独立对话**，只接收上一个角色的**正式产出文档**，不知道上游怎么想的。

```
真实团队工作方式：
  需求分析师 → 产出"需求文档" → 甩给开发者
  开发者只看"需求文档"，不知道分析师怎么分析的
  审查者只看"需求文档+代码"，不知道开发者怎么写的

Just_codding 对应：
  同一个DeepSeek API，换不同 system_prompt 调用
  每个角色 = 一个 LangGraph 节点
  节点间只传产出文档，不传对话历史
  每个角色通过 RAG 独立检索所需上下文
```

**四个角色：**

| 角色 | 对应节点 | Prompt文件 | 职责 | 输入 | 输出 |
|---|---|---|---|---|---|
| 需求分析师 | ANALYZE | `agents/analyst_prompt.md` | 理解需求，产出需求概括 | 澄清文档 + RAG(历史任务) | 需求概括文档 |
| 开发者 | DEVELOP / FIX | `agents/developer_prompt.md` | 规划+写代码 | 需求概括文档 + RAG(源码) | 代码变更 + 实现说明 |
| 审查者 | REVIEW | `agents/reviewer_prompt.md` | 审查代码质量 | 需求概括+代码变更+实现说明 + RAG(规范+错误库) | 审查报告 |
| 侦探型调试 | DIAGNOSE | `agents/debugger_prompt.md` | 定位BUG根因 | BUG描述+日志 + RAG(源码+历史BUG) | 问题分析报告 |

### 3.3 LangGraph 状态图（两个工作流）

#### DEV（增量开发）

```
INPUT_GATE (澄清节点)
   │  追问5个问题，信息足够后产出"澄清文档"
   ▼
ANALYZE (需求分析师)
   │  输入: 澄清文档 + RAG
   │  输出: 需求概括文档
   │  独立上下文，不继承任何对话历史
   ▼
DEVELOP_PLAN (开发者-Plan模式)
   │  输入: 需求概括文档 + RAG(源码)
   │  先规划方案 → agent判断充分 → 自动切Build
   ▼
DEVELOP_BUILD (开发者-Build模式)
   │  输出: 代码变更 + 实现说明
   ▼
REVIEW (审查者)
   │  输入: 需求概括 + 代码变更 + 实现说明 + RAG(规范+错误库)
   │  输出: 审查报告 (通过 / 问题清单)
   │  独立上下文
   ▼
┌───审查通过?
├─ 不通过 → FIX (开发者) → REVIEW (重新审查) ... 循环
└─ 通过 → HUMAN_ACCEPT (等人验收)
              ├─ 人点 [不通过] → 回到FIX
              └─ 人点 [通过] → OUTPUT → 总结面板 + 写入长期记忆 + 更新RAG索引
```

#### DEBUG（BUG修复）

```
INPUT_GATE (澄清节点)
   │  追问BUG细节 → 产出"澄清文档"
   ▼
DIAGNOSE (侦探角色)
   │  输入: BUG描述 + 复现步骤 + 日志 + RAG(源码+历史BUG)
   │  输出: 问题分析报告 (根因 + 论据链)
   ▼
┌───论据够不够定位根因?
├─ 不够 → ADD_LOGGING (加日志) → HUMAN_WAIT (暂停，等人复现贴日志) → DIAGNOSE (重新分析)
└─ 够了 → FIX (开发者)
              │  输入: 问题分析报告 + RAG(源码)
              │  输出: 修复代码
              ▼
           REVIEW (审查者-第1轮，查逻辑)
              ▼
           REVIEW (审查者-第2轮，查规范)  ← DEBUG比DEV多一轮自审
              ▼
           ┌──审查通过?
           ├─ 不通过 → 回到FIX
           └─ 通过 → HUMAN_ACCEPT → OUTPUT
```

### 3.4 Function Calling 工具体系

Agent通过FC调用以下工具，这是它的"手脚"：

| 工具 | 用途 | 安全限制 |
|---|---|---|
| `read_file` | 读取源码文件 | 只读，无风险 |
| `write_file` | 写入代码文件 | 路径校验：只能在项目源码目录内，禁止写系统目录 |
| `search_code` | 全局搜索代码内容 | 只读 |
| `execute_shell` | 执行编译、检查命令 | **白名单**：仅允许 `cargo check`、`npm run build`、`npm run lint`、`pytest` 等编译检查命令 |
| `check_token` | 查询已消耗token和预算剩余 | 内部调用，不暴露给AI |
| `save_checkpoint` | 保存断点到SQLite | 内部调用 |

**Plan/Build模式下的FC行为差异：**

```
Plan模式:
  read_file    ✅ 可用
  search_code  ✅ 可用
  write_file   ❌ 禁止
  execute_shell ❌ 禁止

Build模式:
  read_file    ✅ 可用
  search_code  ✅ 可用
  write_file   ✅ 可用（路径校验后）
  execute_shell ✅ 可用（白名单内）
```

Agent通过调用 `save_checkpoint` 函数在Plan完成后请求切Build模式，编排层检查token预算和plan完整性后放行。

## 四、RAG系统详解

### 4.1 存什么（四个索引库）

| 索引库 | 内容 | 分块方式 | 用途 |
|---|---|---|---|
| 代码索引 | 项目全部源码文件 | Python AST解析，按函数/类分块，每块≤500token | 开发/修复时注入相关源码 |
| 任务记忆 | 历史工作流总结（每次完成的总结摘要） | 每条任务一个块 | 新任务时召回相似任务参考 |
| 错误库 | BUG类型→修复方案的映射 | 每条错误一个块 | 审查时对照检查，修复时参考方案 |
| 规范库 | 编码规范、红线规则条目 | 按规则逐条分块 | 审查时注入规范供对照 |

### 4.2 什么时候查（检索触发时机）

| 工作流节点 | 检索内容 | 检索方式 | 取top N |
|---|---|---|---|
| 澄清节点 | 历史相似任务 | 语义检索（向量相似度） | 3条 |
| 需求分析 | 历史任务 | 语义检索 | 2条 |
| 开发(Plan) | 相关源码 + 历史任务 | 关键词+语义混合检索 | 8(源码) + 2(记忆) |
| 审查 | 编码规范 + 历史错误模式 | 关键词为主 | 5条 |
| 修复 | 当前错误→匹配已知修复方案 | 语义检索 | 3条 |
| 诊断 | 相关源码 + 历史同类BUG | 混合检索 | 8(源码) + 3(历史BUG) |

### 4.3 混合检索实现

```
第1步: 关键词检索 — SQLite全文搜索（LIKE/正则匹配关键词）
第2步: 语义检索 — 查询文本向量化 → 在向量表中计算余弦相似度 → 取top-K
第3步: RRF融合 — 两个结果列表按Reciprocal Rank Fusion算法合并排序
第4步: 注入 — 格式化检索结果，塞进当前节点的system prompt
```

### 4.4 技术选型

| 组件 | 选型 | 原因 |
|---|---|---|
| Embedding模型 | `sentence-transformers` (all-MiniLM-L6-v2) | 80MB本地模型，384维向量，CPU跑足够快，零API费用 |
| 向量存储 | SQLite（BLOB字段存numpy数组） | 零额外依赖，自建余弦相似度检索函数（约20行代码） |
| 混合排序 | RRF (Reciprocal Rank Fusion) | 融合关键词和语义两路检索结果 |

## 五、记忆系统详解

### 5.1 短期记忆（Session级别）

一个工作流session内的上下文，session结束后归档。

```sql
-- 会话
sessions: id, type(dev/debug), status(running/paused/done/failed), created_at

-- 对话消息（当前上下文窗口内）
messages: id, session_id, role(system/user/assistant), content, token_count, created_at

-- 中间产物（节点产出文档）
artifacts: id, session_id, type(clarification/requirement/code_changes/review/summary), content, created_at
```

### 5.2 长期记忆（跨Session）

每个工作流完成/失败后自动写入：

```sql
long_term_memory:
  id, category(task/error/preference),
  title, content(text),
  embedding(blob),  -- 用于语义检索
  source_session_id,
  created_at, last_recalled_at
```

**写入时机：**
- 工作流成功完成 → 自动生成任务总结存入
- 审查发现问题 → 错误模式存入错误库
- 代码文件变更 → 增量更新代码索引（只索引变更文件）

**检索时机：**
- 新任务开始时 → 语义检索相似历史任务
- 遇到编译错误/逻辑问题 → 匹配已知错误模式+修复方案
- 用户提到"跟上次XXX类似"时

### 5.3 上下文窗口管理

DeepSeek上下文上限128K token。角色隔离后单节点窗口压力不大，但仍需管理：

```
策略：滑动窗口 + 摘要压缩

当前节点内部已跑N轮对话：
  最近5轮：保留完整对话
  第6-N轮：用LLM压缩成300字摘要
  摘要保留：关键决策、文件路径、错误信息、待办事项

完整对话历史存入SQLite（事后回溯用，不塞进上下文窗口）
```

## 六、安全与成本控制

### 6.1 Token预算

```
DeepSeek V3 参考定价（以官网为准）：
  输入: 2元/百万token
  输出: 8元/百万token

一个完整DEV流程预估：
  澄清对话   5K token
  需求分析  10K
  开发(Plan)  5K
  开发(Build) 15K
  审查      10K
  修复      10K
  RAG注入    5K
  ─────────────────
  合计      60K token ≈ 0.3元

5元硬上限 ≈ 支撑15次以上完整开发
设硬上限是为防死循环（审查-修复无限循环消耗token）
```

**实现：** 每次AI调用前估算token数，累加后判断是否超过阈值。超限时中断当前节点，输出"已完成到步骤X，剩余未完成清单"，不静默失败。

### 6.2 Shell命令白名单

```python
SHELL_WHITELIST = [
    "cargo check -p", "cargo build -p", "wasm-pack build",
    "npm run build", "npm run lint", "npm run typecheck",
    "pytest", "python -m pytest",
    "git diff", "git status", "git log --oneline -",
]
# 不在白名单内的任何命令 → 拒绝执行 + 记录日志
```

### 6.3 错误处理策略

| 场景 | 处理 |
|---|---|
| API调用超时(>30s) | 重试3次，仍失败→标记失败，输出已完成总结 |
| API返回异常 | 重试3次，记录错误，跳过失信节点 |
| 编译失败 | 审查节点自动检测 → 触发修复循环 |
| 预算超限 | 中断当前节点，输出已完成总结，不静默失败 |
| 进程崩溃 | LangGraph checkpoint自动恢复，从断点续跑 |
| 白名单外命令 | 拒绝执行，记录日志 |

## 七、面试高频问答（预埋弹药）

### 问1：你跟GitHub Copilot/Cursor/Devin有什么区别？

**答：** Copilot是代码补全工具，我的是多角色工作流编排工具。核心差异：模拟真实团队协作（需求分析师→开发者→审查者），每个角色独立上下文、只看产出文档，自带审查循环和token预算管控。日常编码用Copilot，独立小需求端到端交付用我。

### 问2：为什么用LangGraph而不是直接调API？

**答：** 两个工作流本质是有向状态图。LangGraph天然支持节点/边/条件分支/checkpoint。Checkpoint是关键——token预算有上限，跑一半崩了重头来浪费钱，断点续跑是刚需。另外显式定义每一步的进出比AgentExecutor黑盒循环更可控。

### 问3：单模型自我审查可靠吗？又当运动员又当裁判？

**答：** 坦诚说，确实不如多模型交叉审查可靠。但做了弥补：(1)审查者完全独立上下文，切断思维惯性；(2)审查prompt刻意强调批判性；(3)至少2轮自审，每轮换角度；(4)RAG注入历史错误模式对照检查；(5)DEBUG比DEV多一轮审查。真实项目会升级为多模型交叉审查，MVP阶段够用。

### 问4：上下文窗口128K不会爆吗？

**答：** 核心设计就是角色上下文隔离。每个节点独立上下文，只接收正式产出文档，不继承上游聊天记录。加上滑动窗口摘要压缩，单节点消费约5K-20K token，6个节点约80K，离128K上限有48K余量。实际运行中一个节点很少超过30K。

### 问5：Agent跑崩了怎么办？

**答：**(1)LangGraph checkpoint断点续跑，不重头来；(2)每个节点3次重试+30s超时；(3)预算超限时输出已完成总结，不静默失败；(4)编译失败自动触发修复循环；(5)底线：最差情况回到人手里，但至少有已完成的工作记录。

### 问6：RAG为什么自己写向量检索，不用ChromaDB/FAISS？

**答：** 几十个文件的简历项目，不需要分布式向量库。SQLite存向量+自写余弦相似度=20行代码，零外部依赖。但设计上理解了Embedding原理（分块策略、向量化、相似度计算、RRF融合排序），未来数据量大了切FAISS只需换存储层，检索层接口不变。面试官想看的是技术选型的思考过程，不是无脑堆重武器。

### 问7：token预算5块钱怎么定的？

**答：** 按DeepSeek V3官方价算，一个完整DEV流程约60K token≈0.3元，5块钱能跑约15次。设硬上限是防死循环（审查-修复来回跳），不是真怕超支。面试官要看你有没有成本意识。

### 问8：怎么保证Agent不会删你的项目代码？

**答：** 白名单命令机制+写文件路径校验+Plan模式先禁写。但坦诚说，命令执行安全是缓解不是杜绝，本地开发机跑的前提就是信任。生产环境需要沙箱。

### 问9：你自己写了多少代码？框架帮你做了多少？

**答：** 分三层说：
- **框架做的**：LangGraph状态编排、HTTP请求、SQLite连接
- **我做的核心设计**：(1)多角色工作流+上下文隔离方案；(2)RAG混合检索+自建向量存储+RRF融合；(3)token预算管控+断点续传；(4)Plan/Build模式自主切换逻辑；(5)审查轮次自适应决策
- **差异化价值**：不是我调了什么API，而是我**设计了什么约束和规则**

### 问10：你的项目局限性和下一步计划？

**答：** 局限性：(1)单模型审查不如多模型交叉可靠；(2)白名单覆盖面有限；(3)只支持DeepSeek一个模型。下一步：(1)接入至少1个其他模型做交叉审查；(2)支持可配置的白名单；(3)增加多项目并行支持。

## 八、技术栈总览

| 层 | 选型 | 原因 |
|---|---|---|
| 后端框架 | FastAPI | Python异步框架，原生WebSocket支持（进度推送需要），与LangGraph生态兼容 |
| 前端 | Vue 3 (Composition API) | 轻量，SFC单文件组件，适合进度面板 |
| 编排引擎 | LangGraph | 有向状态图，节点/边/条件分支/checkpoint天然适配两个工作流 |
| AI API | DeepSeek | 兼容OpenAI格式，支持function calling，性价比高 |
| 数据库 | SQLite | 零配置，本地运行，够存对话+向量 |
| Embedding | sentence-transformers (all-MiniLM-L6-v2) | 80MB本地模型，384维，CPU跑，不调外部API |
| 向量检索 | 自建（SQLite + 余弦相似度） | 20行代码，零额外依赖 |
